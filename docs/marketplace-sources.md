## Snapshot identity and artifact integrity

Both distributions are parentless generated snapshots. Their canonical commit,
builder ZIP hashes, immutable distribution commits and native results belong in
the owner's post-publication source record linked above. A snapshot cannot embed
its own future Git commit or ZIP hash. Do not use a historical version's identity
as the current expected revision.

Codex CLI 0.167.0 accepts both a slash-named branch and an immutable commit for
`--ref`. A branch is a mutable review channel. For an immutable installation,
take the Codex commit for `0.5.0a2` from the published record and use it as
`--ref`. If the record does not list that version, stop and ask the owner.
Claude Code 2.1.308 accepts a named `#ref` branch and rejects raw SHAs as
nonexistent branch names. Do not create a fake SHA-named branch.

For Claude on the measured POSIX surface, register and inspect the native clone
before plugin install:

```sh
claude plugin marketplace add 'https://github.com/keitruong191/KKdesign-kit.git#review/claude-0.5.0a2'
git -C "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/plugins/marketplaces/kkdesign-kit-marketplace" rev-parse HEAD
```

Install only when that HEAD equals the Claude distribution commit recorded for
`0.5.0a2` in the published source record. Stop if the version is absent or the
commit differs; obtain owner review rather than guessing. After it matches:

```sh
claude plugin install kkdesign-kit@kkdesign-kit-marketplace --scope user
claude plugin list --json
```

This verifies registration-time identity, not immutable client-side pinning.
Inspect HEAD again after marketplace update. Native commands affect the chosen
profile; maintainer probes use fresh private profiles and copy no credentials.
No end-user source clone/build is needed.

## Provenance and maintenance

The canonical workflow remains in the integration/task source branch. Each
provider's ZIP is generated by its existing `scripts/build_*_marketplace.py`
from one clean canonical commit, extracted unchanged and committed on a new
parentless distribution branch. Distribution snapshots are packaging outputs,
not a second maintained workflow source. Do not edit the generated plugin.
`PROVENANCE.json` records canonical commit, builder, version, archive SHA-256
and every extracted file's SHA-256. Its inventory excludes itself. Bundle
verification additionally checks the skill's canonical resource inventory.
Hashes verify bytes, not publisher identity or human approval.

Before publication inspect the builder allowlist and every output path, scan
for private data/credentials/local paths, verify both extracted skill bundles,
and verify that only the built catalog/plugin tree plus provenance is staged.
Use a new review ref if one already exists; inspect history first and never
force-push or overwrite another publisher's work. Publish only those new refs,
without merging main/integration or creating releases/tags. Follow-up evidence
can name a distribution commit only after it exists; that evidence-only source
commit is deliberately not recursively embedded in its own snapshot.

Native updates remain provider-owned. Review branches may move in future only
under explicit review and normal fast-forward publication; a commit pin stays
on its snapshot. A same-version payload change may remain cached by a provider,
so publish a new version for changed plugin bytes. Catalog names are stable;
a profile cannot register two different sources with the same marketplace name.
Remove the old registration before intentionally selecting another snapshot.
No auto-update behavior, production approval or official directory listing is
promised. Private runtime caches and project data remain outside plugin ownership.
